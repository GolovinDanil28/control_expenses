# Project Context

## Purpose

`control_expenses` — приложение для учёта личных/семейных расходов:
фиксация транзакций, категории, бюджеты, отчётность и аналитика трат.

> ⚠️ Точные цели, роли пользователей и границы продукта фиксируются в
> `openspec/specs/` по мере описания идеи. Этот файл описывает **как** мы
> разрабатываем, а не **что** именно строим.

## Tech Stack

- **Язык:** Python 3.12+
- **Пакеты/venv:** `uv` (предпочтительно) либо `pip` + `venv`
- **Конфигурация проекта:** `pyproject.toml` (PEP 621)
- **Тесты:** `pytest` (+ `pytest-cov`)
- **Линтер/формат:** `ruff` (lint + format), `mypy` (strict)
- **БД (ожидаемо):** SQLite через `SQLAlchemy 2.x` + `Alembic` для миграций
  *(уточняется в первой спецификации)*
- **CLI/UI (ожидаемо):** `typer` для CLI; веб-слой — уточняется
  *(FastAPI / Streamlit / другое — фиксируется в спецификации)*

## Project Conventions

### Code Style

- Python 3.12+, полная аннотация типов, `mypy --strict` без ошибок.
- Формат и линтинг — `ruff format` + `ruff check` (настроен в `pyproject.toml`).
- Именование: `snake_case` для функций/переменных, `PascalCase` для классов,
  `UPPER_SNAKE_CASE` для констант.
- Модули маленькие, одна ответственность; докстринги на публичных API
  (Google-style).
- Никаких магических чисел в бизнес-логике — только именованные константы.
- Деньги **никогда** не хранятся/считаются как `float` — только
  `decimal.Decimal` (или целые в минорных единицах).

### Architecture Patterns

- **Чистая архитектура / слои**, зависимость направлена внутрь:
  - `domain/` — сущности, value objects, бизнес-правила. Без I/O и фреймворков.
  - `application/` — use cases (сценарии из спецификаций), порты (интерфейсы).
  - `infrastructure/` — адаптеры: БД, файлы, внешние API, планировщик.
  - `interfaces/` — CLI / HTTP / UI, только разбор ввода и форматирование вывода.
- Один сценарий спецификации = один use case (`application/<capability>/...`).
- Ошибки бизнес-правил — типизированные доменные исключения, а не строки.
- Границы возможностей (capabilities) в `specs/` совпадают с пакетами в
  `src/control_expenses/`.

### Testing Strategy

- **TDD в рамках SDD:** сначала требование и сценарий в `spec.md`,
  затем падающий тест, затем реализация.
- Каждый `#### Scenario:` из спецификации должен покрываться минимум одним
  тестом; имя теста отсылает к capability + сценарию.
- Пирамида тестов:
  - unit — доменные правила и use cases на фейковых портах (большинство);
  - integration — репозитории/миграции на временной SQLite-БД;
  - e2e — CLI/HTTP «чёрный ящик» для ключевых пользовательских путей.
- Покрытие бизнес-логики ≥ 90%; CI-гейт: `ruff check`, `mypy`, `pytest`.

### Git Workflow

- Ветка `main` стабильна; работа — в `feat/<change-id>`, `fix/<change-id>`.
- Имя ветки/PR = change-id из `openspec/changes/` (kebab-case).
- Коммиты в стиле Conventional Commits:
  `feat(expenses): add recurring transactions`, `docs(specs): ...`.
- PR обязателен и должен ссылаться на change: «Spec: openspec/changes/<id>».
- Мерж только после зелёного CI и проверки соответствия кода спецификации.

## Domain Context

- **Транзакция** — движение денег (расход/доход/перевод) с датой, суммой,
  категорией, счётом/кошельком, опциональными тегами и заметкой.
- **Категория** — иерархическая классификация трат (еда, транспорт, жильё…).
- **Бюджет** — лимит на категорию/период (месяц, неделя, кастомный).
- **Отчёт** — агрегация за период: траты по категориям, динамика, отклонение
  от бюджета.
- Терминология, валюты, множественные счета и синхронизация уточняются в
  первой спецификации и далее дополняются по мере развития.

## Important Constraints

- Работает офлайн; никаких обязательных внешних сервисов.
- Данные пользователя приватны: локальное хранилище, экспорт/импорт по запросу.
- Точность денежных расчётов и идемпотентность повторного импорта — обязательны.
- Простота ввода: транзакция фиксируется минимумом полей за секунды.

## External Dependencies

- На старте — отсутствуют. Возможные будущие (фиксируются отдельными
  спецификациями): банковские выписки (CSV/OFX), уведомления, бэкап в облако.
