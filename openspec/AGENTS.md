# OpenSpec Instructions

Инструкции для AI-ассистентов, работающих с этим репозиторием
(Spec-Driven Development через OpenSpec).

## Читай в этом порядке

1. `openspec/project.md` — контекст проекта, стек, конвенции (обязательно).
2. `openspec/specs/**/spec.md` — текущее **истинное состояние** продукта.
3. `openspec/changes/<change-id>/` — активная работа (предложение → сборка).

## Ключевые понятия

- **Спецификация (`specs/<capability>/spec.md`)** — как система работает СЕЙЧАС.
  Правится только вместе с реализацией и только после архивации change.
- **Change (`changes/<change-id>/`)** — предложение изменений: что и почему
  делаем. Живёт до момента внедрения.
- **Capability** — возможность продукта (`expenses`, `budgets`, `reports`…).
  Одна capability = одна папка спецификации ≈ один пакет в коде.

## Формат спецификации (обязателен)

Каждое требование:

```markdown
### Requirement: <название в свободной форме>
Система SHALL <формулировка требования>.

#### Scenario: <название сценария>
- **WHEN** <условие/вход>
- **THEN** <ожидаемый результат>
```

Правила:

- Требование — ровно одно чёткое утверждение; модальные глаголы
  **SHALL / MUST / SHOULD / MAY** (избегаем should для обязательного).
- У каждого требования **минимум один** `#### Scenario:`. Сценарий = контракт,
  по нему пишется тест. Уровень `####` строгий — иначе валидатор не увидит.
- Сценарии пишутся WHEN/THEN (допускаются AND, но без вложенности).
- Никаких деталей реализации (имена таблиц, библиотек, полей API), если они
  не наблюдаемы снаружи. Спецификация описывает **поведение**.

## Операционные модели

- **Create-only в `changes/`:** deltas в `changes/<id>/specs/` описываются как
  `## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements`
  / `## RENAMED Requirements`.
- **MODIFIED** требует скопировать требование целиком и поправить — не фрагмент.
- **REMOVED** требует строку `**Reason**: ...` и `**Migration**: ...`.
- **RENAMED** — `FROM:` / `TO:`; новые имена используем во всех остальных delta.
- В `specs/` заголовки `## ADDED|MODIFIED|REMOVED|RENAMED` не встречаются —
  только `## Purpose` + `## Requirements`.

## Рабочий процесс

### 1. Разведка / уточнение
Читаем `project.md` и релевантные `specs/`. Задаём вопросы, пока объём change
не станет ясен. Ничего не пишем в код.

### 2. Propose
Создаём `openspec/changes/<change-id>/`:
`proposal.md`, `tasks.md`, при необходимости `design.md`,
и deltas в `specs/<capability>/spec.md`.
`change-id` — kebab-case, глагол-сущность: `add-expense-entry`,
`update-budget-alerts`.

### 3. Validate
`openspec validate <change-id> --strict` (или `--all`) — должно быть зелёным
до старта реализации. Плюс самопроверка: у каждого требования есть сценарий,
сценарии проверяемы, термины согласованы.

### 4. Implement
Работаем по `tasks.md` по порядку, помечая `- [ ]` → `- [x]` сразу после
выполнения пункта. Порядок внутри change:
спецификация → падающий тест → реализация → рефакторинг.
Коммиты ссылаются на change-id.

### 5. Archive
После мержа: `openspec archive <change-id>` — deltas применяются к `specs/`,
change переносится в `openspec/changes/archive/YYYY-MM-DD-<change-id>/`.
`specs/` после этого снова описывает реальность.

## Правила AI-ассистента

- Не пиши код раньше, чем требование и сценарий зафиксированы в спецификации.
- Одна сессия — один change. Расширение объёма = новый change, а не тихая
  правка существующей спецификации.
- Не правь `specs/` напрямую — только через архивацию change.
- Расхождение кода и спецификации — баг: либо чини код, либо предлагай change.
- Формат задач в `tasks.md`: `- [ ] X.Y <формулировка>` — один шаг ≈ один
  коммит, проверяемый результат.
- Соблюдай конвенции `openspec/project.md` (типы, `ruff`, `mypy`, `pytest`,
  слои архитектуры, `Decimal` для денег).

## Полезные команды

```bash
openspec list                       # активные changes
openspec validate --all --strict    # проверка формата и структуры
openspec show <change-id>           # дельты change
openspec archive <change-id>        # применить дельты к specs/
```

```bash
uv run ruff check . && uv run ruff format --check .
uv run mypy src
uv run pytest
```
